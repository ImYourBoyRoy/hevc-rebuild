# HEVC Rebuild Studio desktop app

This is the Ubuntu-first desktop application for HEVC Rebuild. Rust owns environment/settings reads, read-only discovery and profiles, app-launched input batching, and no-repair toolchain version/capability resolution with encoder smoke checks. Rust also owns content-tune previews and run-time tune selection, resource/YouTube forecasts, starting/retry thread plans, live Linux resource sampling and observations, FFmpeg/x265 argument planning, compressed-stream packet fingerprints, HDR10+ verification/extraction, Dolby Vision eligibility checks, live memory/swap/disk guard decisions, FFmpeg child-process supervision, fixed-schema report-row appends, and validated-output commit/rollback for Rust-launched GUI, CLI, and MCP encode calls. Python interprets progress, adapts Rust-sampled resources, passes validated selections, prepares report values, performs Matroska metadata changes, and retains HDR-profile, expected Matroska-tag/poster checks plus the full direct-engine validation fallback. Rust checks selected output streams, copied payload identity, track parameters, timing, dispositions, and chapter invariants for Rust-launched jobs. Rust owns calibration eligibility and workload fingerprints, constructs bounded null-output commands, and handles cache checks, candidate process/resource monitoring, pressure rejection, and layout selection for Rust-launched jobs; Python retains the remaining HDR/container metadata comparisons and direct-run compatibility while parity work continues. Direct Python runs keep the reference tune resolver, toolchain resolver, discovery, argument planner, HDR process helpers, process runner, resource planner, sampling, guards, report writer, and transaction fallback. Start with the root [README](../README.md) and [project instructions](../AGENTS.md) for supported systems, build prerequisites, engine behavior, and safety boundaries.

From this directory:

```bash
pnpm install --frozen-lockfile
pnpm tauri dev
```

## Toolchain and dependency versions

Use Node 24.21.0 from the repository `.nvmrc` for the recommended LTS build. `package.json` supports Node 22.17+, 24, and 26 and pins pnpm 12.10.1 with its `packageManager` field. Enable Corepack when available, or install that pnpm version directly. Tauri Rust crates and the JS API/CLI use 2.12.1; the dialog plugin uses 2.8.1. The dependency ranges use compatible-major floors; `pnpm-lock.yaml` records the exact resolved versions used by frozen installs. SvelteKit 3 configuration lives in `vite.config.js`.

Rust dependencies use caret requirements with full lower-bound versions, and `src-tauri/Cargo.lock` pins the resolved graph. The streaming verifier uses RustCrypto `sha2` 0.11.0, compatible with the current Rust 1.99 toolchain. Rustup's stable toolchain is the supported build channel. The normal `pnpm check` path uses TypeScript 6 for compatibility; TypeScript 7.0.2 is installed alongside it through the upstream npm alias and can be checked with `pnpm check:tsgo`. Keep the TypeScript 7 check opt-in because SvelteKit 3 and svelte-check still require TypeScript 6 on the default checker.

The Python engine currently has no third-party Python package dependencies. FFmpeg, FFprobe, MediaInfo, and MKVToolNix remain explicit system tools. The longer-term Rust-engine migration is tracked in the root `todos.md`.

To build the configured Ubuntu Debian installer and AppImage:

```bash
pnpm tauri build
```

The Media Library is the starting point and the only scan queue. It shows each file as a poster card with its title, current name, proposed name, and matching state. Click a card to open a poster-first review with a large poster, alternate artwork, and the title, year, certification, and plot. Mark Animated on the card, then choose rename, metadata-only MKV, or rebuild for the selection. Stream and memory detail stays inside the card. Environment setup lives in Settings and the setup status links directly to that section. The interface uses a larger type scale, coordinated sage-and-paper Light surfaces, and graphite Dark surfaces with theme-aware status icons. Three distinct instrument skins remain available: Phosphor (CRT terminal), Ion (radar console), and Breach (alarm surface). Saved Hacker preferences migrate to Phosphor.

The **Help** section explains the main screens, scan and rename steps, required Ubuntu media tools, command examples, and how to connect the local MCP stdio server. Native pickers accept multiple files or folders, and files/folders can be dropped onto the app; each source is scanned into the saved queue. The GUI schedules selected files across ready queue sources, or new and queued files for the chosen task when nothing is selected; completed, failed, skipped, interrupted, and needs-review results are held out until selected. Each source runs in sequence and uses its saved scan settings. Stop-after-current and stop-on-error apply to the complete sequence. Per-file outcomes are saved from the CSV report. Result rows expand to show the saved message and output/report paths, load a bounded 1 MB diagnostic excerpt, open the report, select a file for retry, or mark it skipped. The memory column keeps risk and worker count visible; budget, swap, and pressure-retry details are expandable. If the app closes during a source batch, those files are marked interrupted; files in later batches remain queued. Before another metadata-only, test, or full run can include an interrupted or uncertain file, the GUI shows its saved report row and requires a read-only FFprobe check of the recorded output (or the source path if no output was recorded). A successful report plus a readable recorded output can be explicitly marked complete; other files require review acknowledgment before continuing. The app never resumes encoders automatically, and existing or duplicate output paths remain blocked. For automation across roots, the JSON CLI `json queue-run` and MCP `start_media_queue_run` accept ordered batches. Each source needs an explicit selected-file list, every source uses the same mode, and duplicate canonical files are rejected. During a desktop run, a progress bar stays visible across pages and the matching library row shows the active file's phase and percent. Progress events carry the exact source path to disambiguate duplicate filenames and report elapsed time, encode ETA, input size, current output size, and a changing output-size estimate after 10% progress. Metadata embedding, output validation, installation, and the final report result are distinct stages. The estimate can change with the footage; the completed report records actual size. Live resource telemetry separately reports CPU, RAM, swap, and disk readings.

The queue also records the current stage for each file: scanning, renaming, copying streams, rebuilding video, or validating output. Its status strip groups counts in a stable order, and a restart converts active stages to **Interrupted** for review. The bulk local-poster action lists only selected movie rows from the current organizer and updates their saved artwork choices; it does not copy or replace the image file.

For standard HEVC rebuilds, choose a default folder in **Run & settings → Rebuild output folders** or set a different folder on each file row in **Media library**. The default destination mirrors the input folder structure; a per-file folder overrides it and receives that file directly. Separate destinations keep the original in place. If no separate destination is configured, the validated in-place transaction retains the existing behavior: it moves the original to `old/` only after the replacement passes validation. Existing outputs are never overwritten. Before launch, a Rust planner checks the selected queue across all sources for duplicate or occupied output paths and shows the planned destinations. The engine repeats each source check immediately before writing, protecting against filesystem changes after the preview. These settings persist with application preferences. The GUI planner checks every selected source together. For scripts, `hevc-rebuild-studio json output-plan --request plan.json` and MCP `preview_media_outputs` accept the same read-only multi-source plan; the CLI engine still accepts `--output-dir` and `--file-output-dirs-json`, and MCP `start_media_run` accepts `output_dir` and `file_output_dirs` for test and full rebuilds.

The **YouTube export** task prepares a separate copy for one video or a recursively scanned folder. It makes MP4 copies in a separate `YouTube Uploads` folder by default, defaults to a 1440p target for smaller sources, preserves aspect ratio and source frame rate, never downsizes a larger source, reports Rust-sampled memory/swap pressure and source-volume free space during desktop runs, and reports per-file skips/errors. Rust-launched exports use native sampling, live guard decisions, and FFmpeg process supervision; Python adapts the samples and interprets progress while migration continues. The default **Balanced size** profile targets around twice the source's average overall bitrate, subject to YouTube's published bitrate recommendation; the optional **YouTube bitrate guidance** profile targets the published recommendation and may create much larger files. The GUI shows aggregate and per-file size forecasts plus output-dimension memory forecasts before export and actual size afterward; forecasts vary with content and are not hard size limits. SDR uses H.264/AAC; correctly tagged 10/12-bit Rec. 2020 PQ/HLG uses 10-bit HEVC Main 10/AAC when available. Dolby Vision, incomplete HDR signaling, HDR below 720p, and HDR without 10-bit x265 are skipped. HDR10+ sources are skipped by default because this path does not preserve dynamic metadata; in the YouTube tab, approve that loss on each individual source to export it with static HDR10/PQ signaling. Consent is run-scoped, appears in reports, and is also available via CLI and MCP. Source subtitle streams are omitted from MP4 copies and identified per file; add YouTube-supported captions separately. Upscaling can enlarge smaller sources, but does not restore missing detail or guarantee YouTube's codec or playback tier. Higher-resolution versions may take longer to process on YouTube. Baseline requirements are Python 3, FFmpeg, FFprobe, MediaInfo, libx264, and AAC; HDR additionally requires x265 10-bit. The workflow prepares files; it never uploads or replaces source files.

The YouTube workflow has a dedicated sidebar tab. Resolution, Balanced versus YouTube bitrate guidance, output folder, and an adjustable Balanced size multiplier are editable there and persist with application settings. The default multiplier is `2.0×`; the supported range is `0.5×`–`4.0×`, with a 250 kb/s video floor and YouTube's published video bitrate as the ceiling. Aggregate and per-file estimates update with the selection but are not strict file-size limits. The same multiplier is available to the CLI and MCP run tool.

It reads local NFO metadata first, then can search all enabled sources for each scanned film and detected series. Search results remain attached to the record that started the search; users can compare providers, search another spelling on that item, and review the source record before assigning it. Only the cleaned title is sent; years stay local for ranking, and filenames, paths, NFO text, ratings, local artwork and video contents are not sent.

It is never stored beside the portable app, in browser storage, reports, CLI output or MCP. The Settings page links to [TMDB API registration](https://www.themoviedb.org/settings/api). The required TMDB logo and attribution notice are shown when TMDB results are used; the logo loads from TMDB's official static asset URL and may not appear offline. TheTVDB is available when a user supplies an eligible project API key and optional subscriber PIN, confirms valid access, and saves credentials in the operating-system keyring. Review TheTVDB’s [API access page](https://www.thetvdb.com/api-information/signup) and [v4 API guide](https://github.com/thetvdb/v4-api/blob/main/README.md); project licensing or user-supported subscriptions may be required. The workbench currently uses the default season order. Alternate aired/DVD/absolute anime orders still need explicit selection and review. AniList is excluded while its API terms prohibit using it as local backup or data storage.

The metadata workbench consumes the current Media Library analysis directly, so titles stay connected to the scanned records. Rust checks local Kodi NFO details first and previews nearby movie, show, and season art without playing media. Existing NFOs seed editable fields and suppress automatic provider requests; users can compare public sources or search another title for that record. When no local NFO exists, automatic searches send only the cleaned title; the editable metadata blacklist is applied to imported title clues and search text, while year hints rank results locally. Paths, complete filenames, ratings, NFO text, artwork bytes, and video bytes stay on-device. A malformed NFO is surfaced for review and does not silently trigger an online query. For a TV folder, `tvshow.nfo` is the primary series record; conflicting episode `<showtitle>` values or unreadable episode NFOs block local episode metadata from being applied and identify the files to review. In movie mode, the workbench lists every analyzed film and offers a batch source search; in TV mode, it lists detected series folders and offers batch search for unambiguous shows, including local show titles from `tvshow.nfo` or episode NFO `<showtitle>`. Rust extracts title/year clues from movie basenames and series folders, and can use a shared episode-name prefix in generic library roots. Only a unique exact normalized title-and-year match without a provider conflict is auto-associated; other results wait for review. Each result opens the corresponding film or show assignment for direct editing. Reviewed movie and series metadata, provider/local artwork paths, episode lists, and per-file episode assignments persist with the queue; the Media Library row previews the selected local image or provider poster, shows its proposed filename, and offers a focused item-review dialog. That dialog keeps matching, source details, editable fields, and artwork tied to the selected film/show; **Open full organizer** leads to batch naming and sidecar previews. The post-scan Media Library task chooser routes title and filename review to the organizer for the active source, or sets the existing metadata-only/full-rebuild mode while retaining queue selection and preflight checks. Confirmed renames update cached rows and related paths. Local card previews are lazy and use the native scoped image reader. Explicit local poster choices and reviewed metadata flow into metadata-only MKV, short-test, and full-rebuild outputs; provider posters need an explicit save, and YouTube does not consume these overrides. Opening a TV episode's edit action returns to its associated show. Shared flat folders that do not identify one series are blocked from association. Full-series rename requires a complete organizer scan because the Media Library analysis can omit files below its size threshold. The organizer scans common `SxxEyy` IDs without probing media contents. Movie fields remain independent per file; TV series fields remain associated with the show and episode fields stay per episode. Editable name patterns persist in app preferences, and rename paths are previewed before collision-checked confirmation. Matching NFOs, file-specific local artwork, artwork attribution, common external subtitles, and external audio sidecars are included in the checked plan and follow the video rename. Conflicting or unreadable TV episode NFOs block local series assignment until review. Conflicting scalar fields inside or across same-kind NFO sidecars are reported by filename and field; neither conflicting record is applied. Multi-episode TV naming, embedded-tag association, and a crash-recovery/undo journal remain open.

The full organizer has a direct **Create a tagged MKV copy** action for the current organizer selection. It can follow a separately confirmed rename, then carries just those selected queue items into Metadata-only MKV mode. The Run page shows the destination and whole-queue collision check before starting; the remux copies streams without video encoding, embeds supported reviewed metadata/artwork, validates the output, and keeps the source in place. The Kodi NFO sidecar action is optional and separate.

TV rename review flags possible gaps in observed `SxxEyy` filenames as a check, not proof that media is missing; seasons containing a multi-episode filename are excluded from that heuristic. A filename/provider year mismatch requires an explicit acknowledgment before a TV rename. Truncated or unreadable scans and unselected supported episode files block full-series renames. These checks do not yet cover season-order variants, every special/absolute numbering convention, or safe automated splitting of multi-episode files.

Poster candidates can be explicitly saved as sidecars beside assigned movie files, at the selected series root (`folder.<ext>`), or inside a detected season folder (`poster.<ext>`). Movie sidecars use `[media filename]-poster.<ext>`. A matching `.attribution.json` file preserves provider/source/license information. Downloads use an allowlist of provider-owned HTTPS image hosts, verify JPEG/PNG/WebP signatures, cap each image at 16 MiB, stay within existing directories under the selected root, and refuse overwrites. In **Settings → Poster storage**, **Save poster beside the media** and **Embed poster in the new MKV** are separate choices; enable both to create the `[media filename]-poster.<ext>` sidecar and attach cover art to metadata-only, short-test, and full-rebuild outputs. With sidecar saving off, confirmed provider and local posters stay in the private app profile's `.cache/artwork` folder. The **Saved poster artwork** panel reports total, assigned, and unused cache size. Its reviewed purge only removes app-managed, unassigned poster images plus matching attribution files; queue-assigned posters and unrecognized entries stay untouched. The purge uses a fresh preview ID and does not touch the separate x265 calibration cache. Clearing calibration data would cause eligible large-file jobs to benchmark thread layouts again. Rust validates image type, size, and analyzed-root/private-cache containment before use. Available credit/license information is kept in the attachment description. Provider choices still need explicit save confirmation, and YouTube output does not consume selected-art overrides. Metadata-only output writes a new MKV, verifies its tracks, chapters, tags and cover when embedding is enabled, and leaves the source file untouched.

The metadata workbench can also save reviewed film, TV-show, and selected-episode fields as Kodi-format NFO sidecars. Each movie file carries its own reviewed title, short/long text, genres, rating, and poster selection into the preview; episode fields are edited per episode. It previews exact paths and requires a separate confirmation. It preserves standard NFOs owned by the user and only replaces app-marked sidecars after a current preview. Metadata-only remuxes and full rebuilds read nearest show metadata plus adjacent movie/episode NFOs, maps supported title, show/episode, date, certification, genre, synopsis/summary, source, and rating values into Matroska tags, then validates those tags before installing output. Kodi ratings on the 0–10 scale are divided by two for Matroska's 0–5 `RATING`. Standard NFOs remain preferred by third-party managers; an app-managed fallback suffix may not be discovered by applications that require canonical filenames.

The Rust organizer also has CLI and MCP interfaces. `hevc-rebuild-studio organize scan ROOT` scans one folder; `organize preview PLAN.json` prints an exact no-write preview; `organize apply PLAN.json --preview-id ID --confirm` requires the current preview ID and explicit confirmation. MCP provides `scan_library_names`, `preview_library_rename`, and `apply_library_rename` (which requires `confirmRename=true`, the exact `previewId`, and camelCase item fields such as `sourcePath`). Metadata sidecars use `hevc-rebuild-studio metadata write-preview REQUEST.json` and `metadata write-apply REQUEST.json --preview-id ID --confirm`; MCP exposes `preview_library_metadata_write` and `apply_library_metadata_write` with `confirmWrite=true` and the current `previewId`.

The Media library displays expandable per-track FFprobe and MediaInfo details, per-file stream include/exclude controls, and a per-file **Content tune** control beside each filename. **Automatic** follows that source's saved tune and metadata detector; a reviewed provider genre of Animation or Anime also contributes evidence when automatic animation detection is enabled. **Animated** and **Normal** remain explicit per-file overrides. Without a custom stream map, the saved secondary-video and data-stream policies apply. After a file is customized, every included real-video stream is encoded to HEVC; included audio, subtitles, attachments, and data streams are copied. This can preserve 4K and 1080p versions together in one MKV. At least one real video track must stay selected. The encoder applies an aggregate memory plan for selected video streams and validation checks the selected output streams before the original can be replaced.

In **Settings**, **Filename filters** add case-insensitive include/exclude glob patterns one per row; `*` matches any run of characters, `?` matches one, and exclude patterns take precedence. They apply to file basenames and folder names during scans; changing them requires a new scan. The seeded extra, hidden-name, sample, and trailer rules are removable, while app-owned state folders stay excluded for safety. **Title cleanup** holds removable, case-insensitive text patterns that clean imported title clues before public lookup, rename proposals, and readable output metadata; for example, `Movie*Group` matches `movieReleaseGroup` and `Movieshowgroup`, and only the matching text is removed. The list can be cleared, and **Save app defaults** keeps edits across launches. The RenameTheThings archive contains filename/folder exclusions but no separate editable word blacklist. The cleanup list is supported by the engine CLI (`--metadata-text-blacklist` can be repeated) and MCP (`settings_json.metadata.text_blacklist` is an array); it is not a comma-separated setting. Encoder identifiers and technical statistics are preserved.

**Settings → Poster storage** has two independent switches: **Save poster beside the media** writes `[media filename]-poster.<ext>`, and **Embed poster in the new MKV** attaches the selected cover to metadata-only and rebuilt MKVs. Either, both, or neither can be enabled. Save app defaults at the top of Settings to keep the embedding choice across launches; poster sidecar/cache storage is an application preference.

In Environment & capabilities, set an executable path for FFmpeg, FFprobe, MediaInfo, `mkvpropedit`, `mkvmerge`, or `mkvextract`, then choose **Save paths & check**. Blank entries use PATH; an FFprobe sibling may be detected beside an overridden FFmpeg. CLI callers can use the matching `--<tool>-path` options. MCP `inspect_environment`, `start_folder_analysis`, and `start_media_run` accept a `tool_paths` object; rebuild MCP calls may pass `file_stream_overrides`, mapping absolute media paths to the selected FFprobe stream indices returned by analysis.

The Environment screen, CLI `json environment` action, and MCP `inspect_environment` use native Rust host/tool checks. Rust-launched rebuild and YouTube jobs also use native discovery and a no-repair resolver that checks the selected tools and smoke-tests the requested encoder; it does not install packages. The native discovery path refuses to process a partial list if the 10,000-file cap is reached. Effective settings are resolved by Rust for the GUI, CLI `json defaults`, and MCP `get_effective_settings`, with the same user/app/folder precedence as the Python engine. Read-only media analysis, cached Ubuntu package version checks, reviewed GUI APT setup, digest-verified HDR10+ helper installation, CSV report-history reads and Rust-launched per-file CSV appends, live run-resource snapshots, run-time starting/retry thread planning, per-progress resource sampling, guard decisions, FFmpeg/x265 argument planning, and FFmpeg child-process supervision also use Rust for GUI/CLI/MCP workflows. Python 3 remains required for run orchestration and report-value/log creation, direct Python engine runs, and remaining metadata, validation, HDR, and transaction policy work; direct Python runs retain discovery and toolchain fallbacks plus their CSV writer. The old JSON bridge remains callable directly as a compatibility/reference script, but the Rust application does not launch it. Python adapts native run snapshots, interprets FFmpeg progress, and applies guard decisions to the current retry/report model. These native operations do not make the overall app Python-free.

At launch, the desktop app reads detected tool versions and compares the fixed Ubuntu package list with the local APT catalog. This check is read-only and does not refresh indexes or install anything. In **Settings → Environment & capabilities**, **Review setup & updates** shows missing packages and installed-to-candidate versions together. If the local catalog is stale, the app refreshes it first, then displays the exact plan for review. After confirmation, the Rust backend rechecks the current missing/update lists, simulates the relevant APT plans, blocks removals and unlisted upgrades, installs missing packages, and applies only confirmed updates. When the package operation succeeds, a missing HDR10+ helper is installed from its upstream release after SHA-256 verification. The setup activity then rechecks the environment and can show each affected executable's before/after version and resolved path, including an explicit still-missing result. Live output stays bounded in the current view; per-operation package/helper logs are saved with application state and can be reopened or exported from Settings. Logs redact URL user information, label lines clipped at 32 KiB, and mark truncation at 16 MiB. APT repositories can lag upstream; custom executable overrides are never replaced.

MCP keeps the explicit package flows available through `check_ubuntu_package_updates`, `refresh_ubuntu_package_catalog` (requires `confirm_refresh=true`), and `upgrade_ubuntu_packages` (requires the exact `confirmed_package_names` list). CLI callers can check with `hevc-rebuild-studio json apt-updates`, explicitly refresh with `hevc-rebuild-studio json apt-refresh --confirm`, and upgrade with `hevc-rebuild-studio json apt-upgrade --confirm --package NAME` repeated for every package in the current update list. CLI upgrades block on a stale index or changed package list and simulate the transaction before execution; APT is also given `--no-remove`. MCP/CLI update APIs do not use the desktop combined setup flow and never install the HDR10+ helper implicitly.

`hevc-rebuild-studio metadata artwork save REQUEST.json` downloads one reviewed provider image to the explicit local targets in the request JSON. MCP provides `save_library_artwork` for sidecars and `cache_library_artwork` for the private app cache; these save reviewed image bytes only, and a later MKV output attaches the selected poster only when `metadata.embed_artwork` is enabled. The GUI also offers a confirmed private-cache copy of a locally selected poster.

Inspect the private poster cache from the JSON CLI with `hevc-rebuild-studio json artwork-cache inspect`. After reviewing its counts and `previewId`, purge eligible unused app-managed posters with `hevc-rebuild-studio json artwork-cache purge --preview-id PREVIEW_ID --confirm`. The purge refuses stale previews and protects queue-assigned posters. MCP exposes `inspect_artwork_cache` and `purge_unused_artwork_cache`; the latter requires the exact current `preview_id` and `confirm_purge=true`.

Read-only local metadata/artwork inspection is available over CLI and MCP: `hevc-rebuild-studio metadata assets inspect REQUEST.json` and `inspect_local_library_assets`. The request contains `root`, `mediaPaths`, and `directoryPaths`; the result includes parsed local NFO fields and supported adjacent image paths. It does not contact a provider or return artwork bytes.

The typed MCP `preview_media_outputs` tool checks destination paths across multiple selected roots without reading or changing media. `start_media_run` accepts one root and performs its own preflight. For ordered multi-source batches, `start_media_queue_run` accepts 1–500 source requests using the same run fields, each with a non-empty explicit `selected_files` list. All entries use one common mode; duplicate canonical paths and roots are rejected, and metadata/test/full destinations are preflighted together before processing. `stop_on_error` defaults to true. Each source keeps its own settings, tool paths, and per-file overrides. Matching saved queue rows synchronize from that source’s exact CSV report; absent rows stay `needs_review`. Interrupted or uncertain files require report/output review and exact paths in `acknowledge_review_paths`. The JSON CLI offers synchronous `json queue-run --request REQUEST.json`; progress goes to stderr and the final summary is JSON on stdout. MCP runs in the background, supports `get_job` polling, and accepts a safe-stop request. It also accepts `output_dir` and `file_output_dirs` for short tests or full rebuilds. `output_dir` sets the default folder; `file_output_dirs` maps analyzed absolute media paths to their existing destination folders. `file_poster_overrides` maps media paths to selected local JPEG/PNG/WebP images inside the analyzed input and is limited to short-test/full HEVC outputs. Full rebuilds still require `confirm_full_rebuild=true`; existing targets and duplicate batch paths are rejected before encoding. The tool also accepts `mode="youtube"`, `confirm_youtube_upload=true`, `youtube_resolution`, `youtube_quality_mode` (`balanced` or `recommended`), optional `youtube_source_multiplier` (`0.5`–`4.0`, default `2.0`), an optional absolute `upload_output_dir`, and optional `allow_youtube_hdr10plus_loss_paths` containing only the individually reviewed source paths where dynamic-metadata loss is accepted. HDR10+ files without per-file consent are skipped. Folder-analysis results include per-file size estimates. `inspect_environment` reports YouTube readiness separately from full rebuild readiness. The YouTube task makes separate output copies without moving originals; full rebuild keeps its existing confirmation requirement.

The UI loads settings through the shared Rust resolver and does not maintain a separate defaults table. Choose Light, Dark, Phosphor, Ion, or Breach appearance from the global top bar. The desktop opens at 1600 × 1000 logical pixels, clamped to the current monitor's work area, and remembers the last usable size and maximized state. Window state, application preferences, and saved rebuild defaults share a native JSON file. The AppImage uses a sibling `<AppImage filename>.data/settings.json`; the `.deb` uses the user's XDG config folder. Effective settings follow built-in defaults, user TOML, saved app profile, then library `.hevc-rebuild.toml`; Python engine parsing remains in place for direct engine commands and unported processing. The browser-only preview saves UI preferences in a versioned browser-local key and remains disconnected from system tools.

Right-clicking the desktop app opens a Tauri-native utility menu for choosing a media folder, analyzing the current library, navigating the app, refreshing the environment, and copying a media/library path or diagnostic log when relevant. Editable fields get a native Cut/Copy/Paste/Select All menu. The app suppresses generic webview context menus on its main surface. The browser-only preview suppresses that generic menu outside editable controls; it cannot display desktop-native menus.

The AppImage is not a self-contained media-processing runtime: Python 3 and the external FFmpeg, MediaInfo, and MKVToolNix tools remain system dependencies. Its launcher clears the `PYTHONHOME` value exported by linuxdeploy before starting host Python, so the system standard library is used. Keep the `.AppImage.data/` directory beside the AppImage when moving a portable copy. If that location is not writable, the application reports and uses the per-user config folder.

The built executable also supports the existing engine CLI and a JSON bridge:

```bash
hevc-rebuild-studio cli --help
hevc-rebuild-studio cli "/path/to/Media" --recursive --info-only
hevc-rebuild-studio json environment
hevc-rebuild-studio json scan --root "/path/to/Media" --recursive
hevc-rebuild-studio json queue --offset 0 --limit 100
hevc-rebuild-studio json queue-select --request selection.json
```

Start its local MCP stdio server with `hevc-rebuild-studio --mcp`. Register it in an MCP host as command `hevc-rebuild-studio`, args `--mcp`. Tools expose hardware/environment, effective settings, paged folder analysis, `inspect_media_queue` for saved library pages, `set_media_selection` for the persistent global selection, `inspect_artwork_cache` and reviewed `purge_unused_artwork_cache`, queue-wide `preview_media_outputs`, tracked runs/safe stop, reports and bounded logs, explicit fixed-list system repair, `inspect_local_library_assets` for NFO/artwork inspection, reviewed poster sidecar/cache saves, and NFO/organizer operations. `cache_local_library_artwork` accepts an object with `source_path`; cache purge requires a fresh preview ID and explicit confirmation. Full rebuild and test output require explicit tool confirmation fields. Keep the media scope to local content the user owns or is authorized to process.

Public metadata tools are `search_public_films`, `get_public_film_metadata`, `search_public_tv_series`, and `get_public_tv_series_metadata`. They accept a title phrase or reviewed provider ID and do not read local media. TMDB lookup stays in the GUI and remains attached to the scanned movie or series record; the saved user token is never sent through CLI or MCP.

Folder analysis returns current effective memory totals/availability and a profile-aware x265 concurrency forecast on each supported media file. The forecast is a scheduling heuristic rather than a peak-RAM guarantee; scan again to refresh it after system memory or run settings change. `json scan` and the engine CLI `--info-only` expose the same plan. In automatic mode, a first 4K/large-media run can benchmark up to two short x265 thread layouts, cache the lower-memory near-fastest result for 24 hours, and record the selected layout in the report. Calibration creates no media output and changes only worker/frame counts; the profile-aware cap and live RAM/swap/PSI retry remain active. During an encode, the live status shows system swap occupancy/rates plus FFmpeg's own RSS and `VmSwap`; completed reports retain peak measurements. Sustained swap-in plus full-memory PSI stalls can stop the temporary attempt and retry with reduced x265 concurrency while preserving quality settings. Swap is never automatically resized. Optional 8/16 GiB system-level swap advice remains future work.

Ubuntu `.deb` and x86-64 AppImage outputs are configured. This AppImage build came from Ubuntu 26.04.1 and bundles GTK/WebKit libraries requiring glibc 2.43; it will not run on Ubuntu 24.04. Build the AppImage on Ubuntu 24.04 before claiming compatibility with that release. CLI/MCP packaging and native runtime are not supported or verified for Windows/macOS yet.
