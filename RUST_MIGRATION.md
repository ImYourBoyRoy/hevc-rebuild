# Python-to-Rust Migration Map

## Purpose and current boundary

The Rust application is the target implementation for shared desktop, CLI, and MCP behavior. The existing Python engine remains the behavior reference and runtime for media operations until each stage has equivalent normal, skip, error, reporting, and rollback behavior. Keep the Python implementation available during parity work; do not delete it or label the app Python-free early.

`lib.rs` includes an inventory test that walks the production `hevc_rebuild/` Python package and root entry point and requires each source file to appear in this map. This catches untracked Python modules; it does not claim that mapped behavior has been ported or parity-tested.

Several application-support slices are native. `environment.rs` performs read-only OS, CPU, memory, GPU, binary-version, and encoder-capability inspection, and resolves/smoke-checks the requested media toolchain for Rust-launched jobs that disable dependency repair. `settings.rs` loads built-in defaults and merges user TOML, the saved app profile, and folder TOML with the Python engine's precedence and validation rules. `dependencies.rs` owns the cached Ubuntu package report; `reports.rs` reads report history and appends per-file CSV rows for Rust-launched jobs; `media_scan.rs` owns native read-only discovery, media profiling, and scan-time forecasts. Its private discovery action also supplies file batches to Rust-launched Python compatibility jobs; those batches fail explicitly at the 10,000-file scan limit. `youtube.rs` centralizes YouTube source-aware dimensions, bitrate/size estimates, HDR routing, FFmpeg arguments, temporary MP4 validation, and no-overwrite output install for Rust-launched GUI/CLI/MCP exports. `resource_monitor.rs` samples Linux run-time resources for Tauri/MCP observers and the Rust-launched encoder. `resource_plan.rs` samples host CPU/RAM/swap/PSI for native run planning; `runtime_guard.rs` samples per-progress resources and owns live memory/swap/disk decisions for Rust-launched runs. `encode_plan.rs` constructs the FFmpeg/x265 argument vector from Python's validated profile/selection adapter, and `encode_supervisor.rs` starts FFmpeg, relays progress/diagnostics, reports exit status, and handles cancellation for Rust-launched GUI/CLI/MCP encode calls. `calibration.rs` owns eligibility, machine/workload fingerprints, bounded null-output argument construction, cache checks/writes, Rust-side benchmark process/resource monitoring and pressure rejection, and candidate selection for Rust-launched runs. Python supplies typed profile/options data and keeps the direct-CLI reference implementation. `transactions.rs` owns the final no-overwrite validated-output commit and operation-time original rollback for those same Rust-launched runs. Python still chooses the backup filename, prepares report values/logs, interprets progress, applies run policy, and owns retry/report orchestration; direct Python runs retain their process/planner/transaction/report fallbacks. `packet_verify.rs` provides bounded-memory FFmpeg compressed-stream fingerprints, and `validation.rs` compares selected output streams, copied-payload identity, track parameters, timing, dispositions, chapter invariants, and each encoded video track's static HDR/color and Dolby Vision policy for Rust-launched jobs. HDR10+ dynamic metadata is re-verified against each corresponding output video stream in Rust. Python remains the legacy direct CLI and behavior reference; expected Matroska tag/poster checks, report-value generation, remaining calibration parity, and end-to-end run orchestration remain open migration stages.

For Rust-launched rebuilds, `media_scan.rs` also owns the private `engine-profile` and `engine-profile-tracks` actions. `engine-profile` invokes configured FFprobe and optional MediaInfo for the source; `engine-profile-tracks` reuses that bounded JSON and samples frame details for selected additional video tracks in Rust. Both return bounded results through `probe.py` adapters for the compatibility engine. This removes duplicate Python probing/profile construction from app-launched jobs; direct Python CLI retains its profiler until parity and the engine workflow migrate.

For Rust-launched GUI/CLI/MCP runs, `hdr_metadata.rs` streams selected HEVC data from FFmpeg into `hdr10plus_tool` for HDR10+ verification/extraction and verifies HDR10+ on each encoded output track. It also owns the Dolby Vision safe-preservation and explicit HDR10-fallback reason checks. `validation.rs` rebuilds an output profile for every encoded video track and checks color labels, HDR10/HLG, mastering display, MaxCLL/MaxFALL, and the requested Dolby Vision profile/RPU/EL/compatibility policy before Python can proceed to commit. The Python engine adapts the typed request and keeps its direct-run implementation. HDR10+ reinsertion orchestration, Matroska metadata insertion, expected Matroska tag/poster checks, and error/report decisions remain Python-owned.

For Rust-launched GUI/CLI/MCP runs, `metadata_text.rs` applies validated case-insensitive substring globs and the conservative built-in release-group suffix policy to Matroska/NFO text in bounded batches. `Movie*Group` matches camel-case variants such as `movieReleaseGroup` and `Movieshowgroup`; suffix logic preserves ordinary titles and technical tokens. A versioned response marker lets the Python adapter retain compatibility with older helpers while using Rust's policy when present. Python keeps its direct-run reference and still owns XML traversal, Matroska mutation, and change reporting.

`library_metadata.rs` also exposes a local filename-clue parser to the Tauri workbench. It accepts a basename, extracts a cleaned title plus optional year/range and certification, and rejects path input. `MetadataWorkbench.svelte` uses these clues for user-started batch searches over every analyzed movie and detected unambiguous series folder. Only cleaned titles go to providers; year ranking stays local, and a candidate must be reviewed against its per-file or per-series assignment before editing or writing sidecars. This is an app/UI feature, not evidence that Python media-engine behavior has migrated.

`library_assets.rs` provides the local-first companion to those public providers: it reads bounded movie/episode/show NFO fields and indexes recognized adjacent artwork under a canonical selected library root. The workbench seeds local NFO details and defaults public suggestions to items without local metadata; malformed NFOs stay visible and do not silently fall through to a provider. Users may explicitly search alternatives. Local poster previews are read through a one-image bounded command and returned as data URLs. CLI `metadata assets inspect` and MCP `inspect_local_library_assets` expose only NFO values and artwork paths, not image bytes. Conflicting NFO sources and embedded-container-tag matching remain open; this organizer feature does not imply Python media-engine parity.

## Migration order

1. **Effective settings read path complete in Rust.** Continue parity against the untouched reference ZIP and move run-setting application to shared Rust engine types.
2. Finish native dependency/platform adapters (Linux first, then Windows/macOS), including engine-start package planning/repair, HDR helper verification/install, toolchain resolution, and cross-platform media-tool path handling.
3. Rust read-only discovery, FFprobe/MediaInfo source profiles, tracks, chapters, attachments, content-tune decisions, scan errors, and scan-time forecasts are integrated in GUI, JSON CLI, and MCP. Rust also supplies discovery lists and toolchain preflight for Rust-launched engine jobs; private `engine-profile` and `engine-profile-tracks` actions build source and selected-track profiles for those jobs. Python adapts those bounded results, while direct Python runs keep the Python profiler. Compare behavior with Python and source-ZIP fixtures, and keep the direct engine fallbacks until parity is accepted.
4. Complete the Rust run-resource and process layer. `resource_plan.rs` owns reusable run/scan starting and first-retry plans and samples Linux host resources for Rust-launched runs; `resource_monitor.rs` streams observer snapshots into GUI/MCP and shares the Linux sampler with the encoder; `runtime_guard.rs` samples each Rust-launched FFmpeg progress update and owns live memory/swap/disk decisions; `encode_supervisor.rs` owns app-launched FFmpeg creation, progress relay, exit status, and cancellation/adapter-disconnect cleanup. `calibration.rs` owns eligibility, workload fingerprinting, candidate command construction, execution, pressure rejection, cache operations, and selection; Python supplies typed analyzed profile/options. Next port progress/error interpretation, run-setting/tune application, calibration cancellation/report integration, live guard/retry orchestration, report-value construction, and direct-engine parity; then add Windows/macOS telemetry and process adapters before claiming those platforms.
5. `encode_plan.rs` constructs FFmpeg/x265 encode vectors and `encode_supervisor.rs` owns app-launched encode processes. `content.rs` selects run tunes, `hdr_metadata.rs` handles HDR10+ FFmpeg/tool streaming and Dolby Vision eligibility, and `metadata_text.rs` applies validated text blacklist globs for Rust-launched runs. Add reusable cross-language golden fixtures, then move remaining run-setting application, calibration cancellation/report integration, Matroska metadata edits, HDR10+ reinsertion orchestration, and quality-neutral retry policy into Rust while retaining the direct-Python reference until parity is proven.
6. Finish output validation and metadata handling. Rust now verifies selected-stream order/count, copied payload hashes, track parameters/timing/dispositions, chapter invariants, and every encoded track's HDR/color/Dolby Vision policy for Rust-launched GUI/CLI/MCP runs, including per-track HDR10+ dynamic metadata verification. Port expected Matroska tag/poster verification and Matroska edits, then move the remaining final-gate policy to Rust. Keep direct Python fallback until parity is proven.
7. Finish Rust run orchestration, report-value generation/logs, and YouTube output. `youtube.rs` owns source-aware per-file YouTube policy, FFmpeg arguments, and MP4 validation; Python still batches files, applies HDR10+ consent, handles collision/skip and resource retry flow, prepares reports, and commits the temporary copy. `reports.rs` appends fixed-schema per-file CSV rows for rebuild jobs, and `transactions.rs` owns the validated-output commit/rollback operation; Python still builds report values/logs, chooses backup paths, and coordinates full-rebuild validation gates.
8. Remove Python runtime/source from release packages only after the parity matrix and representative Ubuntu, Windows and macOS package/runtime gates pass.

Each stage must keep external GUI, CLI, JSON, MCP, saved-settings and portable-settings contracts aligned. Record dependency updates separately from feature migration, prefer current stable compatible releases, and keep lockfiles reproducible.

## Evidence for the native environment slice

- At the native-environment checkpoint, `cargo test --locked` passed 45 tests, including environment/settings/dependency/report modules and CLI APT argument validation. The latest full suite passes 53 tests.
- Current-host Python and Rust environment reports agree on OS support, effective CPU count, memory/swap, GPU IDs, tool checks, encoder capabilities, readiness and missing APT package recommendations. Memory numbers can differ slightly because each report samples the live machine at a different time; the Python launcher may also rewrite `PATH` for the selected Python runtime.
- The packaged CLI binary's native environment action was exercised with `/usr/bin/ffmpeg` and detected its sibling `/usr/bin/ffprobe`; a nonexistent FFmpeg path returned a structured unavailable check instead of aborting the report.
- The packaged executable completed MCP `initialize`, listed 23 tools, and returned all 17 checks from MCP `inspect_environment`.
- Native UI interaction, package installation/launch, and Windows/macOS behavior remain unverified.

## Evidence for native settings resolution

- Rust resolves built-in defaults, user `engine-config.toml`, saved `settings.json` profile, then root `.hevc-rebuild.toml`; it does not create any settings files. The desktop command, JSON CLI `defaults`, and MCP `get_effective_settings` use the same resolver.
- Four Rust tests cover default preservation, all source-precedence layers, null app profiles, invalid TOML/table shapes, setting ranges, and duplicate blacklist patterns.
